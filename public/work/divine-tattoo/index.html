The problem

A tattoo studio needed a responsive public website and a way to manage its own portfolio without editing the website’s source every time an image changed.

The work grew into an authenticated admin interface connected to application data and image storage.

My role

I worked through requirements, frontend changes, backend integration, debugging and deployment using AI coding tools. I inspected the generated changes and used the project to learn how the public site, admin interface, authentication, database and storage fit together.

This was AI-assisted development. It is not a claim that I independently wrote every implementation detail from memory.

What the system does

  • Renders published portfolio work on the public website.
  • Lets an authenticated client upload images and manage portfolio entries.
  • Supports publish, unpublish and delete operations.
  • Persists portfolio ordering through position edits and a database operation.
  • Uses membership checks, tenant-scoped data operations and storage access rules to separate public viewing from protected changes.

Architecture

Public website → published portfolio data + image URLs.

Authenticated admin → membership check → scoped database operations and storage uploads.

The separation between authentication and authorization became a central lesson: signing in is only the beginning of deciding which operations a person may perform.

What I learned

  • Auth and authorization solve different problems.
  • Database policies and storage policies both need attention.
  • Upload restrictions and generated filenames are useful parts of the flow.
  • Ordering must be saved in data, not only rearranged in the UI.
  • Preview, test, review and verify before releasing a change.

Security work is an ongoing learning area. This case study describes implementation work; it does not claim an independent audit or a guarantee that every deployed policy has been verified.
